# Store deployment from GitHub Actions

The existing CI and prerelease workflows test and package KiCad Online. The
separate `Deploy verified store release` workflow submits an **existing** GitHub
release to one store at a time. It never rebuilds a release or runs code from a
downloaded archive. Altium beta is not a deployment target.

This workflow is prepared in source. It is not operational until it is merged
to `main`, the environments and account credentials below are configured, and a
maintainer completes the first live acceptance run. Local mocked tests do not
prove store authentication or publication.

## One-time setup

Create GitHub environments `store-vscode`, `store-chrome` and `store-firefox`.
Set repository variable `STORE_RUNNER` to an isolated GitHub-hosted larger Linux
runner label with at least 102 GiB free on each relevant volume. The first step
checks workspace, temporary and home volumes before downloads, retaining the
100 GiB reserve plus a 2 GiB deployment allowance. A standard hosted runner may
fail this check. Shared self-hosted runners are refused until a proper storage
reservation mechanism is provided. The check is advisory admission control,
not an OS quota; the final step reports remaining capacity.
Restrict deployment to `main` and enable required-reviewer protection where the
repository plan supports it. Protect changes to workflows and deployment code.
The workflow also refuses to run outside `wayri/KiCad-Online` on `main`.
Do not put publishing credentials in source files, issue comments, chat, artifacts
or extension runtime settings. These are maintainer deployment credentials,
separate from users' repository browsing and review accounts.

| Environment | Configuration |
| --- | --- |
| `store-vscode` | Variable `VSCE_VERSION`: an exact reviewed `@vscode/vsce` release supporting `--oidc`. No PAT. |
| `store-chrome` | Variable `CHROME_PUBLISHER_ID`; secrets `CHROME_CLIENT_ID`, `CHROME_CLIENT_SECRET`, `CHROME_REFRESH_TOKEN`. |
| `store-firefox` | Secrets `AMO_API_KEY` and `AMO_API_SECRET`. |

### VS Code

In publisher `wayri` → **Trusted Publishing**, create a policy for owner `wayri`,
repository `KiCad-Online`, workflow filename `store-deploy.yml`, environment
`store-vscode`. The job requests a short-lived GitHub OIDC token and passes the
verified VSIX to `vsce publish --oidc --packagePath`. It does not run package
build hooks. Pin and review the CLI version before enabling submissions.

[Microsoft Trusted Publishing instructions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#publish-with-github-actions-and-trusted-publishing).

### Chrome

Enable the Chrome Web Store API in the publisher's Google Cloud project and
complete the initial OAuth setup with scope
`https://www.googleapis.com/auth/chromewebstore`. Store the resulting client and
refresh credentials only as environment secrets. Google account two-step
verification remains enabled. This implementation uses Google's documented
refresh-token flow; service-account federation can replace it later, after a
separate account-access review. OAuth consent applications left in testing mode
may have short-lived refresh credentials; use an appropriate production setup.

The script targets only extension `klfdjlbngpoopegjmbajaidgodpmjaoc`. It stops if
there is any submitted revision, policy warning or takedown. It never cancels a
review. Successful uploads are submitted with normal review, warning blocking,
and automatic publication after approval. Listing text, screenshots, disclosure
changes and new agreements remain dashboard work.

[Google API setup](https://developer.chrome.com/docs/webstore/using-api).

### Mozilla

Generate API credentials in the existing AMO publisher account. They authorize
actions as that account; use a dedicated publisher account where appropriate
and rotate them if exposed. The script targets the existing add-on GUID
`kicad-visual-review@wayri.github.io`, uses the listed channel, and sends the
original Firefox ZIP without repacking it.

Prepare and audit the matching readable-source companion using the established
[Firefox procedure](FIREFOX.md). Attach
`kicad-visual-review-amo-source-VERSION.zip` to the **same GitHub release** and
record its SHA-256. This step is not yet generated by the release workflow:
the companion includes pinned upstream sources and reproduction instructions,
not just GitHub's automatic source archive. Do not use a source ZIP from another
version. The operator supplies the reviewed source hash when dispatching.

The script validates the extension upload, creates the new version with source
attached, updates checksum-verified release notes and the custom license fetched
from the exact release commit (not current `main`), and checks source
readback. An existing version is inspected, never overwritten automatically.
If a request fails after creating a version, inspect that version manually before
retrying; notes or license metadata may need completion. No mutation is retried
automatically and no existing review is deleted or disabled.

[AMO submission API](https://mozilla.github.io/addons-server/topics/api/addons.html#version-create)
and [API authentication](https://mozilla.github.io/addons-server/topics/api/auth.html).

## Deploy a release

1. Complete release gates, native/browser acceptance appropriate to the changes,
   and the existing GitHub prerelease workflow or audited manual release procedure.
2. In **Actions → Deploy verified store release → Run workflow**, select `main`,
   the exact version tag, and one store. Leave **Submit** unchecked first.
   For Firefox also provide the audited companion hash.
3. Inspect the verification receipt. It checks the tag's resolved commit,
   `sourceDirty: false`, manifest checksum, package checksum in both inventories,
   packaged version and Marketplace/AMO identity. Checksums detect changes against
   the release inventory; they are not an independent signed build attestation.
4. Repeat with **Submit** checked and approve the environment if required.
5. Inspect store status. A successful command means upload/submission acceptance,
   not completed store review. Record actual status in [release status](../RELEASE-STATUS.md).

Runs for the same store are serialized across versions. Each job has read-only
GitHub contents permission and OIDC permission; none can create releases, modify
source or cancel reviews. Receipts contain package hashes and status, not tokens.
Provider errors intentionally omit response bodies that might echo secrets or
private reviewer information. Use the dashboard to diagnose those errors.

The initial workflow is deliberately manually dispatched. Automatically deploying
every published prerelease would also publish versions prepared only for testing.
After live acceptance, a reviewed production-release trigger can be added without
changing artifact verification or environment protections.
